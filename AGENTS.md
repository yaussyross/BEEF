# AGENTS.md — operating instructions for this repo

Instructions for any AI agent (or new human) working in `yaussyross/BEEF`.
Read `docs/HANDOFF.md` first — it's the entry point — then the docs in the order
listed there. This file is the rulebook.

## The product, in one line

BEEF is a free, ads-supported gay male social app for friends, dates, and
hookups: a Grindr-style proximity grid with its own campy brand, privacy-first
architecture, and safety/moderation built in. The owner-endorsed business plan
is `docs/BUSINESS.md` (verbatim) — it is the strategy authority.

## Hard constraints — never violate these

1. **18+ gate is enforced at the DB/API layer, not just the UI.** The DB
   trigger `users_assert_adult` (`db/migrations/0005_triggers.sql`) rejects
   under-18 birthdates; `/api/register` rejects them server-side too. Never
   weaken this, and never return a user's birthdate in any payload another user
   can read (public views expose only `is_adult` + `age_bucket`).
2. **Location stays server-side; clients only ever get bucketed distance.**
   Precise lat/lng is written to `locations` and never selected into any
   response. Grid responses contain distance **bucket strings** only
   (`<1 mi`, `1–5 mi`, …, `nearby`). The only exception: a remote who opts into
   `coarse_location='exact'` may receive a distance rounded to 0.1 mi. Raw
   coordinates must never appear in any API, chat, moderation, or ad payload.
3. **No third-party ad SDK receives location in v1.** `ad_inventory` is
   server-side and coarse-region scoped only.
4. **Content must be suggestive, never sexually explicit** (Apple App Store /
   Google Play policy for dating apps). The moderation pipeline in
   `backend/src/lib/moderation.ts` encodes the "saucy, not smutty" line: paid
   sex / slurs are **blocked** on arrival; explicit terms are **flagged** and
   blurred pending human review — never an auto-ban. Human review + user
   reports are the real enforcement. Re-audit the keyword lists before store
   submission, and leave the identity vocabulary (top/bottom/daddy/twink/…)
   alone — that's ordinary gay-dating language, not explicit content.
5. **No copy of Grindr's trade dress** (colors, tiles, icons, name). Original
   branding throughout. No fake claims, no fabricated users (demo profiles are
   seeded only with `signup_source='synthetic_demo'` and stripped before store
   review).
6. **Never commit secrets.** `.env*` is gitignored (root, backend, app);
   `.env.example` holds placeholders only. CI runs with **no** secrets —
   it never runs migrations or smoke tests against a live DB. Before every push
   (the repo is public), grep for connection strings, keys, tokens, real
   emails/phone numbers, and real user data.

## The one privacy bug class to remember

`@neondatabase/serverless` returns Postgres **enum arrays** (e.g.
`profiles.intent_tags`) as a raw string `"{friends,chat}"`, not a JS array —
and `Array.isArray(x) ? x : []` silently empties them. Any SELECT of an
enum-array column MUST cast it: `intent_tags::text[] AS intent_tags` (done in
`me`, `profile`, `profile.$id`, `grid` — keep it that way in new queries). Do
not "fix" the guard; fix the query.

## Commands that must work

```bash
cd backend
bun install                      # deps
bun run build                    # MUST run before type-check on a clean checkout
node_modules/.bin/tsc --noEmit   # reports EXACTLY 5 pre-existing serve.ts errors (Bun globals); tolerate only those five, never add new ones
bun run start                    # serves 0.0.0.0:3000 incl. /api/ws
cd ..
DATABASE_URL=... bun run db:migrate   # apply migrations (idempotent, no-op re-runs)
```

Frontend/Flutter: `flutter analyze` must be clean; CI also runs
`flutter build apk --debug`. The `android/`/`ios/` folders are generated, never
committed — do not hand-edit them.

## Git workflow (required)

1. Pull latest `main`; branch from it: `git checkout -b <what>/<short-name>`.
2. Commit small, descriptive changes. Push the branch to `origin`.
3. Open a PR with `gh pr create` (or the GitHub UI). CI must be **green before
   asking for review** — the backend job and the Flutter job both run on every
   PR.
4. Never merge your own PR unless explicitly told to; the team lead merges.

## Known gotchas

- `db.ts` exports `sql = () => neon(url)` — always call `sql()`\`…\`` (tag the
  returned function), never `sql`\`…\``. Server-only.
- `serve.ts` pins port 3000 / 0.0.0.0 and frees the port across users before
  binding (last publish wins). Don't read `PORT`/`HOST` from env for the site.
- `src/routeTree.gen.ts` is generated by the build (and gitignored) — don't
  hand-edit or commit it. Same for `dist/`.
- TanStack Start API routes use `createFileRoute('/api/x')({ server: { handlers: { GET/POST: ... } } })` — there is no `createAPIFileRoute` in this version.
- TS errors in `src/` are not tolerated; only the five known `serve.ts` errors
  pass CI. Fix anything new before pushing.
