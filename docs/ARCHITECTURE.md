# BEEF — Architecture

Written from the code in `main` (see `docs/STATUS.md` / `docs/RUNBOOK.md` for
state and commands). The backend is a single **Bun + TanStack Start** process
that serves both the landing site and the mobile REST API, and doubles as the
WebSocket host for 1:1 chat. The client is a **Flutter** app; the database is
**Postgres (Neon)**.

```
landing page + REST API (TanStack Start) ─┐
1:1 chat WebSocket (Bun.serve, /api/ws) ──┤→ same process: backend/serve.ts, port 3000
Postgres via @neondatabase/serverless ────┘
Flutter app (app/lib) → talks to the same host's REST API + /api/ws
```

## Backend layout (`backend/`)

| Path | Role |
|------|------|
| `serve.ts` | Production server. Serves `dist/client` static assets, delegates everything else to the built TanStack handler, and hosts the chat WebSocket at `/api/ws` via `Bun.serve({ websocket })`. **Pins port 3000 / 0.0.0.0** on purpose (the public surface is a single origin; see gotchas). |
| `src/db.ts` | `sql = () => neon(url)` — lazy per-call connection from `DATABASE_URL`. **Must be called as `sql()`\`...\``, never `sql`\`...\``.** Server-only; never import it in client code. |
| `src/router.tsx` | TanStack router bootstrap (`routeTree.gen.ts` is generated by the build and gitignored — never hand-edit; `@ts-nocheck`). |
| `src/routes/` | Filesystem routes: `index.tsx` (landing page + waitlist), `__root.tsx` (HTML shell), `api/*` (REST). |
| `src/lib/` | `auth.ts`, `chat.ts`, `moderation.ts`, `ncmec.ts`, `privacy.ts`, `http.ts`. |
| `src/ws/chat.ts` | The WebSocket hub (see below). |
| `scripts/import-waitlist.ts` | Imports a JSONL waitlist into `waitlist_emails` (env `WAITLIST_FILE`; dedupes via `citext UNIQUE`). |
| `publish.sh`, `go-live.sh`, `build-vercel.sh`, `vercel-entry.ts`, `SITE.md` | **[this-platform only]** ship tooling for the original sandbox/vercel host. Not needed to run the app; re-host the site on your own host. |

### REST route map (`backend/src/routes/api/`)

All routes return JSON; protected routes require `Authorization: Bearer <access-token>` and return `{ error, message }` on failure (via `src/lib/http.ts` — note `errorResponse` maps one specific DB exception to `underage` 403).

| Method & path | Auth | Purpose |
|---|---|---|
| `POST /api/register` | – | Create user. Validates email + password (min 8) + birthdate; **18+ checked here and again by a DB trigger**; `ON CONFLICT DO NOTHING` + atomic user/profile insert → `email_taken` 409. Returns `{ user, accessToken, refreshToken }` (201). |
| `POST /api/login` | – | `{ email, password }` → tokens. Rejects non-`active` accounts; never returns birthdate. |
| `POST /api/refresh` | refresh token in body | Rotate tokens; rejects if the account is not `active`. |
| `GET /api/me` | ✔ | Own profile: email/status/display_name/bio/intent_tags/photo_verification_status/hide_distance. **Birthdate is never selected.** Intent tags use `::text[]` (see gotchas). |
| `GET/PUT /api/profile` | ✔ | Own full profile (the *only* place the owner ever sees their own birthdate) / update bio, intent_tags, interests, coarse_location, hide_distance. No location returned. |
| `GET /api/profile/:id` | ✔ | Sanitised *public* view of another user: `{ user: { id, display_name, bio, intent_tags, photo_verification_status, is_adult, age_bucket, interests } }`. **Never** birthdate, never any location; excludes deleted/suspended/banned users, hidden profiles, and blocks in either direction. |
| `GET /api/grid` | ✔ | The proximity grid. Query: `limit` (≤100), `offset`, `radius_mi` (≤1000), `intent` (friends\|chat\|date\|hookup). PostGIS `ST_DWithin` against the **coarse** centroid (or `travel_geog` when travel mode is on). Ordering: distance bucket → `updated_at` → interest-overlap → user_id. Returns `{ items: [{ user_id, display_name, bio, intent_tags, photo_verification_status, distance, shared_interests, last_active_at }], next_offset, has_more }`. **Distance is a bucket string** (`<1 mi`, `1–5 mi`, `5–20 mi`, `20–50 mi`, `50+ mi`, or `nearby`); no coordinates ever. |
| `POST /api/location` | ✔ | Upsert precise lat/lng — **the only place precise coordinates exist, server-side**. Body: `{ lat, lng, coarse_location? (exact\|city\|region), travel_mode?, travel_lat?, travel_lng?, hide_distance? }`. Derives the coarse centroid; returns only `{ ok: true }` — neither precise nor coarse coordinates are ever echoed back. |
| `GET/POST /api/threads` | ✔ | Inbox list (newest-activity first, unread counts, other participant's public summary, blocked threads excluded) / create-or-fetch the 1:1 thread with `{ other_user_id }` (201; `self_thread`, `blocked`, `user_not_found` guards). |
| `GET/POST /api/threads/:id/messages` | ✔ | REST fallback for chat: history (newest-first, keyset pagination via `cursor`/`next_cursor`) and send. Same domain logic as the WebSocket. POST returns 201 (or 200 + the stored row for a duplicate `client_message_id`). |
| `POST/DELETE /api/block` | ✔ | Block/unblock `{ blocked_user_id }`. A block is enforced **in both directions** everywhere it matters (grid, public profile, chat read/send) and force-closes both users' live sockets immediately (`dropSocketsForPair`). |
| `POST /api/report` | ✔ | Report intake only (`report_type`, `reason`, `reported_user_id`/`message_id`/`thread_id`, optional `is_csam`). Writes `reports` + enqueues a moderation row. Does **not** run vision AI and does **not** transmit to NCMEC (those are later-phase). A message/thread report only resolves if the reporter is a participant. |
| `GET /api/moderation/queue` | `X-Moderation-Key` header | Admin: list the queue (filter by `status`,`target_type`,`limit`,`offset`), enriched with a 240-char content snapshot; never any location. **503 when `MODERATION_ADMIN_KEY` is unset or <16 chars** — routes refuse to run open. |
| `POST /api/moderation/review` | `X-Moderation-Key` header | Admin: `{ queue_id, decision: approve\|reject\|blur\|ban }` applied to the right table by target type, then the queue item is marked reviewed. |

## WebSocket chat hub (`backend/src/ws/chat.ts` + `src/lib/chat.ts`)

- Wired in `serve.ts` via `Bun.serve({ websocket })` at **`/api/ws`**; TLS is
  terminated by the host reverse proxy.
- **Auth before upgrade**: `Authorization: Bearer <jwt>` header (native clients)
  or `?token=<jwt>` (browser WebSocket). Verified with the same access-token
  verifier as REST.
- Protocol (JSON text frames): client → server `{type:"send", thread_id? | recipient_id?, client_message_id, body}` and `{type:"read", thread_id}`; server → client `connected`, `ack` (with `duplicate` flag), `message` (delivered to recipient), `read_ack`, `error`, `blocked` (sent before the socket is closed on block).
- Idempotency: `(sender_id, client_message_id)` unique → retries return the stored row (`duplicate: true`), never a double insert.
- Offline delivery: a message to an offline recipient is persisted; they hydrate history on reconnect via the REST fallback.
- The live socket registry lives on `globalThis` (`__BEEF_CHAT_HUB__`) so the REST block route — which runs inside the *bundled* TanStack handler — reaches the same registry the Bun-level callbacks use (two module instances, one process, one registry).
- Shared domain logic in `src/lib/chat.ts` (thread get-or-create with the sorted-pair key, block enforcement on every read/send, keyset-paginated history, inbox with unread counts) so REST and WS can never diverge. Every message passes the text screen (`screenText`): `block` verdicts are refused ("Keep it saucy, not smutty."), `flag` verdicts are stored `blurred` and queued for human review.

## Auth & JWT (`backend/src/lib/auth.ts`)

- Passwords: bcrypt (bcryptjs, 10 rounds). Never stored or compared in plaintext.
- Tokens: **HS256 JWTs** signed with `JWT_SECRET` (env, must be ≥32 chars).
  Access token: 15 min, audience `beef:access`; refresh token: 30 days,
  audience `beef:refresh` — a refresh token can never replay as an access token
  (audience mismatch). Issuer `beef`. Rotation on `/api/refresh`; v1 tolerates a
  stolen refresh token until expiry (revocable token store is a noted later
  hardening item).
- `requireAuth(request)` parses the Bearer header and returns the user id — used
  on every protected route.
- Accounts: `users.status` is `active | deleted | suspended | banned`; login and
  refresh reject anything but `active`.
- `isAdult(birthdate)` is the server-side 18+ check (register route); the DB
  trigger (`users_assert_adult`) is the backstop.

## Privacy model (`backend/src/lib/privacy.ts`) — exactly what is/isn't returned

One hard rule, enforced in code: **precise lat/lng never leaves the server.**

- **Client → server only**: the owner posts their own precise lat/lng to
  `POST /api/location`. It is written to `locations.precise_lat/lng/geog` and
  never selected into any payload.
- **Coarse centroid**: `coarseCentroid(mode, lat, lng)` blurs the precise point
  — `exact` (user's explicit opt-in: the point itself), `city` (~0.1° cells,
  ≈7 mi), `region` (~0.5° cells, ≈35 mi). Everything the grid queries talks to
  `locations.coarse_geog` (GIST-indexed), never `precise_geog`.
- **Bucketed distance only**: `distanceLabel()` converts a computed distance
  into what a *viewer* may receive:
  - `hide_distance` → the string `"nearby"` (no number at all);
  - remote `coarse_location = 'exact'` → the remote opted into exact placement,
    so a distance rounded to 0.1 mi is returned;
  - otherwise → a coarse bucket: `<1 mi`, `1–5 mi`, `5–20 mi`, `20–50 mi`,
    `50+ mi`. Bucket boundaries must stay in sync with the `bucket_rank` CASE in
    `src/routes/api/grid.ts` (ordering only — the raw rank is never returned).
- **No raw coordinates anywhere in any response**: grid, public profile, inbox,
  chat payloads, moderation queue — none carry lat/lng or the birthdate.
  Public profiles carry only `is_adult` + `age_bucket` (derived, never the raw
  birthdate).
- **Ad story (v1)**: `ad_inventory` is region-scoped and rendered natively by
  the server against a *coarse* region; there is no programmatic ad SDK, and no
  location of any kind is sent to a third party. `post /api/location`'s travel-mode
  ignores live GPS while travelling.
- Image moderation (Google Vision SafeSearch) sends **only image bytes + an
  opaque photo uuid** — never a user id or location (see below).

## Moderation pipeline (`backend/src/lib/moderation.ts`, `ncmec.ts`)

"Sauce Check" — the store-approval story in one module; two layers:

1. **Text screening** (`screenText`): always-on, zero-network keyword classifier.
   Verdict priority **block > flag > allow**:
   - `commercial_solicitation` (FOSTA/paid-sex terms incl. money amounts) →
     **block** the write;
   - `hate_or_abuse` (slurs, self-harm incitement) → **block** the write;
   - `suggestive` (explicit terms) → **flag**: content is stored blurred and
     queued for human review with a friendly re-do prompt — never an auto-ban.
     Role/identity vocabulary (top/bottom/daddy/twink/…) is deliberately absent
     — that's ordinary gay-dating language.
2. **Image screening** (`moderateImage`): calls Google Cloud Vision SafeSearch
   (adult/racy/violence) with **only image bytes + content id**. Env-gated on
   `IMAGE_MODERATION_API_KEY`; when absent or on failure the verdict is
   `pending_human` — the upload stays blurred (photo `status = 'pending'`) and
   is queued; it is never blocked by a missing key. Approved photos go live;
   rejected photos are removed.

**Queue + review**: `moderation_queue` rows are enriched (`listModerationQueue`)
with truncated content snapshots (no location), and a human applies
`approve | reject | blur | ban` via `/api/moderation/review`
(`applyReviewDecision`) — blur is the default friendly outcome, ban is the last
resort. Admin gate is a shared secret header `X-Moderation-Key` checked against
`MODERATION_ADMIN_KEY` (≥16 chars, else routes 503).

**NCMEC / CSAM (`ncmec.ts`)**: a legal requirement wired *before* launch.
`preserveEvidence()` snapshots offending content (text + sha256 hash) into
`report_evidence`; `disableAccountForCsam()` suspends the account. The actual
CyberTipline submission is a **stub that does NOT transmit** (`transmitted:
false`) — replacing it with the real integration (owner-provided credentials,
human-reviewed) is a pre-launch TODO.

## Database (`db/migrations/`)

16 tables (15 in `0003_tables.sql` + `report_evidence` in `0008`), migrations
`0001`–`0008`, **idempotent** (`IF NOT EXISTS` / `DO` blocks / trigger
recreate), applied in filename order. `db/migrate.sh` (psql) and
`db/migrate.ts` (Bun/Neon) track applied files in `schema_migrations` so
re-runs are no-ops. Requires the `postgis` + `citext` extensions (both on Neon).

| Migration | Contents |
|---|---|
| `0001_extensions.sql` | `postgis`, `citext`. |
| `0002_enums.sql` | 14 enums in `DO` blocks: `user_status`, `intent_tag` (friends/chat/date/hookup), `coarse_location_mode`, `verification_status`, `moderation_status`, `photo_status` (+`blurred` added in 0008), `report_type`, `report_status`, `ncmec_status`, `moderation_target`, `moderation_source`, `moderation_queue_status`, `ad_placement`, `ad_kind`, `push_platform`. |
| `0003_tables.sql` | `users`, `profiles`, `profile_photos`, `interests`, `profile_interests`, `locations`, `chat_threads`, `thread_participants`, `chat_messages`, `blocks`, `reports`, `moderation_queue`, `waitlist_emails`, `ad_inventory`, `push_tokens`. |
| `0004_indexes.sql` | GIST on `locations(coarse_geog)`/`precise_geog`, GIN on `profiles(intent_tags)` + `profile_interests`, chat/thread/block/report/moderation/ad indexes. |
| `0005_triggers.sql` | **18+ gate** (`users_assert_adult` — rejects any insert/update whose birthdate is <18 years ago, i.e. `birthdate > CURRENT_DATE - INTERVAL '18 years'`; also rejects NULL birthdate); `locations_sync_geog` (keeps geography columns in sync from the plain lat/lng doubles — `ST_MakePoint(lng, lat)` order!); thread-touch + updated_at triggers. |
| `0006_seed_interests.sql` | Seed interest taxonomy (no users; demo profiles later carry `signup_source='synthetic_demo'` and are stripped before store review — never fabricated as real users). |
| `0007_chat_thread_pair_key.sql` | Move the 1:1 dedupe key onto `chat_threads` (`participant_low/high` unique — collapses (A,B)/(B,A) to one thread); 0003 had keyed it on the membership table. |
| `0008_moderation.sql` | `content_moderation_status` enum (approved/pending/blurred/rejected) for `chat_messages.moderation_status`, `photo_status.blurred`, and `report_evidence` (CSAM evidence snapshot). |

### 18+ gate

Triple-layered: client-side age check (Flutter onboarding) → server-side
`isAdult()` at `/api/register` → **DB trigger** `users_assert_adult` as the
hard backstop. Public payloads never contain the birthdate.

### Enum/intent-tag handling (the one real bug that was found)

`@neondatabase/serverless` returns Postgres **enum arrays** (e.g.
`profiles.intent_tags` of type `intent_tag[]`) as a raw string like
`"{friends,chat}"` — not a JS array (only built-in `text[]`/`int4[]` parse to
arrays). Any handler guard `Array.isArray(x) ? x : []` silently empties them.
The fix (applied everywhere intent tags are read: `me`, `profile`, `profile.$id`,
`grid`): select `intent_tags::text[] AS intent_tags`. Single enum scalars
(`coarse_location`, `moderation_status`, …) return as plain strings — fine.
Keep this in mind for any new enum-array read.

## Things a fresh reader must know (gotchas)

1. `sql()` is a function — call `sql()`\`…\`` (tag the returned handle), never
   `sql`\`…\``.
2. `tsc --noEmit` reports **exactly five pre-existing errors, all in
   `serve.ts`** (Bun globals under the Vite tsconfig). CI tolerates only those
   five (see `ci.yml` for the exact line filter). `src/` type-checks clean —
   don't add new errors.
3. Build order in CI matters: `bun run build` **first** generates
   `src/routeTree.gen.ts` + `dist/server/server.js`, which `tsc` needs to
   resolve route types. On a clean checkout, type-checking before build fails.
4. `serve.ts` pins port 3000/0.0.0.0 deliberately and frees the port across
   users before binding (last publish wins). Don't read `PORT`/`HOST` from env
   when running the site.
5. Flutter `android/` + `ios/` platform folders are **not committed**; CI
   generates them (`flutter create` into a throwaway dir) and copies only the
   scaffolding back, so hand-written `lib/`/`pubspec.yaml` are never clobbered.
6. No secrets in the repo: `.env*` is gitignored (with `!.env.example`);
   migrations never run in CI; CI needs no `DATABASE_URL`/`JWT_SECRET`.
7. The smoke suite that produced the team's 83/83 is **not committed** (see
   `docs/RUNBOOK.md` for how to re-verify endpoints by hand).
